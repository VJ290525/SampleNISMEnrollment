Enrollment Dashboard Product Requirements

Version: 0.1 | Date: 15 October 2026 | Status: Proposed for review
Project: NISM Sync | Task: #58203 | Task assignee: Varsha Jadhav

Purpose and scope

Provide authorized NISM operations users with one dashboard to understand enrollment activity, compare exam demand, act on profiles awaiting review, and inspect upcoming exam sessions and available seats. The confirmed scope comes from the task description: enrollment trends, exam distribution, profile review controls, and upcoming sessions with seat availability. Requirements below propose detailed behavior for review; they do not represent approved NISM business rules.

Release one includes summaries, filters, accessible charts and equivalent tables, profile review navigation and actions, and upcoming session listings. Payment collection, refunds, candidate enrollment, capacity editing, session scheduling, exam delivery, and bulk profile approval are outside this proposed release.

Users and permissions

Proposed roles are dashboard viewer, profile reviewer, and administrator. Map these capabilities to existing NISM roles before implementation. Viewers can inspect only their authorized organizational and centre scope. Reviewers additionally inspect profile details and perform permitted review actions. Administrators manage access through the existing administration workflow. A dashboard role does not automatically grant candidate document access.

Enforce authorization on every data request and action, including direct links. Aggregate totals, chart data, profile queues, and session details must use the same authorized scope. Mask personal identifiers in the queue; reveal necessary details only in the authorized profile review screen.

Dashboard structure and navigation

Place the page title, refresh control, and last successful refresh time above global filters. Follow with enrollment summary and trend, exam distribution, profile review queue, and upcoming sessions. Each section has a descriptive heading and a loading, empty, error, and ready state. Use existing portal navigation and visual conventions.

Selecting a chart segment or summary opens the corresponding enrollment list with its filters preserved. Selecting a profile opens its review details. Selecting a session opens session details in read-only mode. Returning to the dashboard preserves the current filters, sort, and page where possible. If a linked destination is unavailable, show a clear message and retain dashboard access.

Filters and time rules

Proposed enrollment filters are enrollment date range, exam, centre, and enrollment status. Default the enrollment period to the current calendar month in Asia/Kolkata and show those dates explicitly. Apply filters together through an Apply control; Reset restores defaults. Validate that the start date is not after the end date and reject invalid requests without changing the displayed results.

The enrollment date filter applies to enrollment summaries, trends, and exam distribution. The profile queue uses its own submission date and review status filters, defaulting to all pending profiles. Sessions use a separate session date range, proposed as today through the next 30 days. Label each date field so users do not mistake an enrollment date for a session or profile submission date. Exam and centre filters apply only where a valid source relationship exists; otherwise mark the filter as inapplicable to that section. Confirm the filter mapping before build.

Interpret user-selected start and end dates as inclusive local dates, implemented from the start date at 00:00 to the day after the end date at 00:00 exclusively. Display dates and refresh timestamps with IST labels. Bucket trends by enrollment creation time converted to IST.

Enrollment metrics and trends

ED01 Enrollment count. Count distinct enrollment IDs matching the selected date, exam, centre, status, and authorized scope. Count enrollments, not distinct candidates: one candidate with two enrollment IDs contributes two. Exclude deleted and test records according to an approved source flag. A payment retry must not create an additional count for the same enrollment ID.

ED02 Status breakdown. Show the count for each source enrollment status using the same population. Status categories must be mutually exclusive; their counts must reconcile to the total. Agree the source status mapping before using business labels such as confirmed, pending, cancelled, or expired.

ED03 Trend. Plot enrollment counts by day, with weekly or monthly grouping selectable. Include zero-count intervals and readable axis labels. Provide the same values in an accessible table. Daily buckets must sum to the displayed total for the selected period. Do not add comparison percentages until the comparison period and eligibility rules are approved.

Exam distribution

ED04 Distribution. Show exam name, enrollment count, and share of the filtered enrollment total. Share equals exam count divided by the total multiplied by 100. When the total is zero, show no percentage and a no-enrollments message. Round displayed percentages to one decimal; explain that rounded values may not sum to 100 percent.

Use stable exam IDs for grouping so renamed exams do not split counts. Display unmapped records as Unspecified exam and retain them in reconciliation totals. Present a count-sorted bar chart and an equivalent table. Selecting an exam opens matching enrollments while retaining date, centre, and status filters.

Profile review controls

ED05 Queue. Show a paginated list of profiles awaiting review, with a masked candidate reference, candidate name only where permitted, submission timestamp, current review status, and Review action. Sort oldest pending submissions first. Allow search by exact candidate reference and filtering by review status. Do not display uploaded identity documents on the dashboard.

ED06 Review workflow. Open the existing profile review screen where available. Proposed decisions are approve, reject, or request correction, subject to the existing workflow and required checks. Require a reason for rejection or correction requests; validate required fields before submission. Confirm the decision with the candidate reference and action shown. Disable repeat submission while the request is in progress.

Before saving, recheck permissions, the current status, and record version. If another reviewer changed the record, prevent an overwrite, explain the conflict, and reload current details. An authorized successful decision records actor, timestamp, prior status, new status, and reason in the existing audit mechanism. Refresh the queue only after success; a failed request leaves the previous status visible and permits a safe retry. Notification behavior follows the existing profile workflow and requires separate confirmation if none exists.

Upcoming sessions and availability

ED07 Session list. Show session reference, exam, centre or delivery mode, session date and start time in IST, session status, capacity, booked seats, held seats where applicable, available seats, and booking status. Display scheduled, non-cancelled sessions within the selected session range, including sessions with zero availability. Sort by start time ascending, then session ID. Label booking closed sessions even when seats remain.

ED08 Seat calculation. Proposed available seats equal max(0, sellable capacity minus confirmed allocated seats minus active seat holds). Confirm whether capacity already excludes blocked seats; subtract blocks only when they are included in the source capacity. Expired holds release seats according to the booking system's authoritative rules. Waitlisted candidates do not consume a seat unless the booking system assigns one.

Use the booking system's authoritative availability when it exists. Never infer that a remaining seat guarantees booking eligibility. Availability does not reserve a seat; the booking workflow must revalidate it. If allocations exceed capacity, display zero available and flag the discrepancy for authorized operations users. Missing capacity or failed availability retrieval displays Availability unavailable, not zero. Show last refresh time alongside availability.

Data and operational behavior

ED09 Consistency and freshness. Enrollment aggregates use the same normalized source population and snapshot or effective timestamp. Provide a manual refresh and preserve the selected filters. Proposed refresh target is within five minutes of committed source changes; confirm source capabilities and business expectations. Do not mix values from different filter requests when responses arrive out of order.

ED10 Failure states. Load sections independently. A failed section shows an error and Retry while healthy sections remain usable. If retaining previous data, label it as stale and retain its timestamp. Never display zero to represent a network or permission error. Use an explicit empty state for a successful query with no matching data.

ED11 Usability. Support keyboard navigation, visible focus, descriptive control labels, screen-reader summaries, and text alternatives to chart values. Do not convey review or booking status through color alone. On narrow screens, stack sections and preserve access to every table field. Proposed accessibility target is WCAG 2.2 AA, pending confirmation of the project's adopted standard.

ED12 Performance and privacy. Proposed target: dashboard summaries ready within three seconds at the 95th percentile under the agreed dataset and concurrency; review action acknowledgement within two seconds excluding external dependencies. Validate these targets against a production-sized test dataset before acceptance. Paginate queues and session tables, proposed at 25 rows per page. Avoid candidate names, identity documents, and sensitive search terms in telemetry. Log service errors with correlation IDs for support.

Acceptance criteria

  1. AC01 Scope: A user restricted to one centre cannot access another centre's totals, queue records, sessions, or candidate details through filters, URLs, or service calls.
  2. AC02 Dates: Records exactly at the selected IST start boundary are included; records at midnight after the end date are excluded. Invalid ranges show validation and retain the last valid results.
  3. AC03 Reconciliation: For a controlled dataset, enrollment total equals the sum of daily trend buckets, status counts, and exam distribution counts. Repeated rows for the same enrollment ID count once.
  4. AC04 Distribution: An enrollment with an unmapped exam remains in the total and appears under Unspecified exam. With no enrollments, the dashboard displays an empty state without division errors.
  5. AC05 Review: A permitted decision saves once and produces an audit event. Rejection or correction without a reason is blocked. A viewer cannot submit a review decision.
  6. AC06 Concurrent review: If two reviewers open the same version, a decision by the first prevents the second from overwriting it without reloading.
  7. AC07 Seats: Given capacity 100, confirmed allocations 70, and active holds 5, availability is 25 when no blocked seats apply. Expired holds do not reduce availability. Overcapacity never produces a negative displayed count.
  8. AC08 Sessions: Full sessions and sessions whose booking window is closed remain clearly identified. Cancelled sessions are excluded from the default upcoming list.
  9. AC09 Resilience: A section request failure shows an error rather than zero. Retry refreshes that section and preserves filters. A late response from an earlier filter request cannot overwrite newer results.
  10. AC10 Navigation and access: Drill-down lists retain relevant filters. All controls and review confirmations are usable with a keyboard; chart values are available as text.
  11. AC11 Freshness and performance: Each section displays its effective timestamp. Measured freshness and response times satisfy the approved targets on the agreed representative dataset.

Open decisions and dependencies

Resolve before implementation sign-off: (1) business owner and dashboard audience; (2) existing role and centre scope mapping; (3) authoritative enrollment statuses and deletion/test flags; (4) whether trend measures creation or confirmation date; (5) approved profile transitions, reasons, required documents, and notifications; (6) capacity, blocked seats, holds, cancellations, and booking cutoff rules; (7) applicable exam and centre relationships for profile filters; (8) refresh, performance, accessibility targets, and expected data volumes. The defaults and formulas above are proposals until these decisions are approved.

Dependencies are authorized enrollment and exam data, profile review workflow and audit storage, authoritative session availability, identity and access controls, and a representative validation dataset. Export and bulk actions require separate scope decisions.
