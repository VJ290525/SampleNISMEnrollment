01 Scope and approval

Original work item title: Create Test Cases for Enrollment Dashboard. Revision 1 had no description or acceptance criteria. Confirmed feature scope from #58203 is enrollment trends, exam distribution, profile review controls and upcoming sessions with seat availability. Detailed expectations here trace to a proposed PRD, not approved business rules.

Priority P0: access control, decision integrity, reconciliation, core correctness and recovery. P1: other acceptance coverage and usability. Review priorities with product and QA.

No application, backend, API, load or accessibility tests were executed. This deliverable completes test design only. No Azure Test Plans suite or individual test-case work items were created.

  • G1: Approve source statuses, unknown-status mapping, deletion/test flags and deduplication normalization.
  • G2: Approve creation versus confirmation time, current-month/default dates, weekly boundaries, filter relationships, and section-specific Reset behavior.
  • G3: Approve page size (proposed25) and stable queue tie-breaker. Session tie-breaker proposed start time then ID.
  • G4: Map roles, profile transitions, reason rules/length, document permissions, audit/notification contract, version and retry/idempotency protocol.
  • G5: Approve today-through-next30-days meaning (proposed 15Oct–14Nov inclusive), already-started sessions today, booking cutoffs, and session status mapping.
  • G6: Approve booking authority, capacity/block representation, holds/release boundaries, cancellation release and waitlist semantics.
  • G7: Approve freshness, accessibility standard/browser matrix and representative performance workload/targets. Five-minute freshness, WCAG2.2AA, p95 three-second summaries/two-second acknowledgement remain proposals.

Out of scope: payment/refund processing, enrollment creation, capacity editing, session scheduling, exam delivery, bulk profile approval and export. Booking-path verification is an integration dependency, not a new dashboard booking feature.

Harness

Run mutation/security checks only in an authorized isolated environment.

05 Execution and exit

Execution entry: approved PRD and G1–G7 decisions, deployed identifiable build, role-mapped test users, seeded synthetic data, test adapters and safe audit verification. Block individual cases where their business gate or dependency is unresolved; do not silently convert a proposal into an acceptance rule.

For each run, record case ID, build/environment, date, tester, browser/assistive technology, actual result, pass/fail/blocked, evidence link and defect ID. Restore fixture after mutations; performance runs need their own agreed workload and sample size. Sanitise screenshots and logs.

Proposed release exit: approved scope and business rules, every P0 passes, remaining defects explicitly triaged by owner, access and concurrency checks pass, approved freshness/performance/accessibility targets met. This is a recommendation, not a team commitment.
